# The Vitis HLS image (the HLS corpus's oracle, #1624)

AMD's Vitis HLS checks Silinx HLS as ISE checks the open toolchain: `scripts/hls-vitis.mjs` runs the HLS corpus
(`test/hls-corpus`) through it and compares the C simulation, the ports, the co-simulation and the latency with
Silinx's. Vitis does not target the Spartan-3E: it is not a bitstream oracle.

Vitis HLS comes with **Vivado ML Standard Edition** (the former WebPACK): free, no licence file, for the small
7-series parts (Artix-7, Spartan-7, Zynq-7000). It runs on Linux or Windows x86-64 only: on the ISE runner's machine
it runs in an `linux/amd64` Docker image, as ISE does (on an Apple-silicon host under emulation, several times
slower).

Never committed: the installer, the image, Vitis's outputs and logs.

## Making the image

1. **The installer**, downloaded by the AMD account's owner (it needs the account and its export-compliance form):
   the **Linux self-extracting web installer** of the AMD Unified Installer for FPGAs & Adaptive SoCs
   (`FPGAs_AdaptiveSoCs_Unified_<version>_<date>_Lin64.bin`, a few hundred MB), into a folder of its own on the
   machine with Docker.
2. **The install's choices**, `install_config.txt` beside it: generated by the installer
   (`xsetup -b ConfigGen` in the base image: product `2. Vivado`, edition `1. Vivado ML Standard`; it writes
   `/root/.Xilinx/install_config.txt`), then edited:
   - `Destination=/tools/Xilinx`;
   - `Modules=`: `Artix-7 FPGAs:1`, `Spartan-7 FPGAs:1`, `Zynq-7000 All Programmable SoC:1`, every other device and
     tool `:0` (Vitis Model Composer and DocNav too). Vitis HLS is not a module of its own: the Vivado product has
     it (UG973, 2025.2);
   - `InstallOptions=Acquire or Manage a License Key:0`;
   - `CreateProgramGroupShortcuts=0`, `CreateDesktopShortcuts=0`, `CreateFileAssociation=0`.

   The installer's folder must be one Docker Desktop shares (on the runner's machine, under the ssh config's
   `remoteDir`).

   The install is still tens of GB (the 7-series device files, Vivado's simulator for the co-simulation).
3. **The install**: `bash scripts/vitis-hls-image/install.sh <the installer's folder> <version>` builds the base image
   (`Dockerfile`: Ubuntu 22.04 and the libraries), asks for the AMD account once (`xsetup -b AuthTokenGen`, typed by
   its owner), installs, deletes the installer and the token, and saves the container as `xilinx/vitis-hls:<version>`.

## Running the comparison

    node scripts/hls-vitis.mjs [--filter pointer] [--update]
    node scripts/hls-vitis.mjs --detach [--filter pointer]         # the whole corpus takes hours: in the background
    node scripts/hls-vitis.mjs --collect silinx-vitis-… --update   # its progress, or its results once done

A run's folder on the host is deleted only once `--collect … --update` has saved its results (#1826): a `--collect`
with no `--update` shows them and keeps them there.

`--filter` is a regular expression on the designs' names (#1780), e.g. `--filter '^(modeling-pointers|pipelining-loops)-'`.

The machine is `SILINX_ISE_HOST` (else `~/.silinx/config.json`'s ssh user and host, read at run time, never written
in a file; `local` for the image on this machine); `SILINX_VITIS_IMAGE` (default `xilinx/vitis-hls:2025.2`),
`SILINX_VITIS_PART` (default `xc7a35tcpg236-1`). Each design's `hls_config.cfg` is run with that part, the Vivado
flow's interfaces (`flow_target=vivado`: ap_ctrl_hs, ap_vld, ap_memory, as Silinx makes them) and no IP packaging
(`hls-vitis-run.sh`, in the image, with no network). `--update` writes the numbers and port names
(`test/hls-corpus/vitis.json`) and the README's table.

## Measuring the 7-series' timing (#3516)

The same image has Vivado: `scripts/xc7-timing-vivado.mjs` measures the examples' timing with it, to calibrate nextpnr's
7-series delays (its Fmax 1.2–1.5 times Vivado's on the same netlist). Each example's netlist as Silinx's open flow
makes it (Yosys's `synth_xilinx`, written as an EDIF by the same Yosys) is linked, placed and routed by Vivado (no
`opt_design`: the same netlist), which writes its SDF, its worst paths with each element, its timing summary and its
routes' nodes; nextpnr's Fmax on the same netlist is measured here.

    node scripts/xc7-timing-vivado.mjs --detach [--boards basys3,nexys-a7] [--filter '^(blinky|pong)$']
    node scripts/xc7-timing-vivado.mjs --collect silinx-xc7t-… --update

Vivado runs alone on the machine (the script refuses to start while another container runs), one design after
another. `--update` writes only numbers: `packages/silinx-fpga/research/xc7/vivado-timing.json` (per board and
example: Vivado's and nextpnr's Fmax, the cells' delays, the routes' delays grouped by their wire classes) and the fit,
`packages/silinx-fpga/research/xc7/timing-fit.json` (`scripts/xc7-timing-fit.mjs`: the slice's LUT and flip-flop delays
that replace the stubs of the fork's `gen/xilinx_gen.py`, CARRY4's and the F7/F8 multiplexers' arcs, a delay per wire
class, and the logic and routing scales of the critical paths). Vivado's files are deleted with the run's folder.
`SILINX_VIVADO_IMAGE` (default `xilinx/vitis-hls:2025.2`), `SILINX_VIVADO_TIMEOUT` (a design's, s; default 3600).

## The 7-series' examples against Vivado (#3760)

`scripts/xc7-vivado-compare.mjs` builds each example on the Basys 3 and the Nexys A7 with Silinx's open flow (here), with
Vivado's own flow from the HDL (the application's `run.tcl`), and Silinx's netlist placed, routed and written as a
bitstream by Vivado (its DRC on Silinx's synthesis); both Vivado builds of a design in the same container, one design
after another, alone on the machine.

    node scripts/xc7-vivado-compare.mjs --detach [--boards basys3,nexys-a7] [--filter '^(blinky|pong)$']
    node scripts/xc7-vivado-compare.mjs --collect silinx-xc7v-… --update

`--update` writes the numbers and Vivado's warning lines to `test/xc7-vivado-comparison.json` and the table of
docs/TOOLCHAIN.md (`test/xc7-vivado-comparison.test.js` checks both); Vivado's files are deleted with the run's folder.
